# Fraxtal 项目原型说明书

基于画布的非线性 AI 产品设计决策树

## 1. 项目概述 (Project Overview)

- **项目名称**：Fraxtal
- **核心定位**：一款旨在重塑 AI 辅助产品设计流程的开源工具。
- **核心痛点**：当前基于大模型的对话 UI 呈线性结构，极易导致设计初期的上下文丢失、逻辑污染以及高昂的试错成本。产品设计本质上是一个发散、收敛、再发散的网状过程。
- **解决方案**：将大模型交互与无限画布（类似 Draw.io / 节点编辑器）相结合，打造由“用户问答节点”驱动的、可任意扩展和发散的“设计决策树”。系统承担穷举和逻辑推演工作，用户专注于核心决策与方向把控。

## 2. 核心概念与数据实体 (Core Concepts)

| 概念 | 英文 | 说明 |
| --- | --- | --- |
| 设计画布 | Canvas | 无限拓展的工作区，承载整棵产品设计决策树的拓扑结构。 |
| 决策节点 | Decision Node | 树上的基本单元。每个节点封装了特定的上下文历史、当期面临的问题组以及用户的决策（回答）。 |
| 决策链 | Decision Chain | 从根节点到任意一个特定节点所形成的唯一路径。它代表了一套完整、无冲突的上下文历史，是最终生成产品方案的基准素材。 |

## 3. 核心业务流程与交互规范 (Core User Journey)

整体流程分为五个阶段：

| 阶段 | 名称 | 关键动作 | 关键产出 |
| --- | --- | --- | --- |
| 一 | 项目初始化与根节点生成 | 新建项目，填写初始想法 | 初始根节点 |
| 二 | 节点发散与 AI 逆向提问 | 双击节点，勾选有价值的提问 | 2~3 个追问；待决策列表 |
| 三 | 选项收敛与决策输入 | 逐题选择选项或自定义填空 | 每题 2~4 个结构化选项；【生成决策节点】按钮亮起 |
| 四 | 树形演化与状态派生 | 点击【生成决策节点】 | 连线 + 子节点（继承决策历史） |
| 五 | 一键编译与方案生成 | 点击【生成方案】 | 通过校验后输出产品设计文档 |

### 阶段一：项目初始化与根节点生成

- **操作**：用户新建项目，填写初始想法（系统提供产品描述模板供选填）。
- **响应**：在画布中央生成“初始根节点”。

### 阶段二：节点发散与 AI 逆向提问 (AI Reverse Prompting)

- **操作**：用户在画布上双击任意节点，打开“大模型问答窗口”。
- **响应**：
  - 系统基于当前节点所承载的“决策链历史”，自动在窗口顶部提出 2~3 个当前阶段最有价值的追问 / 发散性问题。
  - 提供【换一批】按钮，用于重新生成提问。
- **交互**：用户从 AI 的提问中勾选认为有价值的项，将其加入下方的“待决策列表”。

### 阶段三：选项收敛与决策输入

- **操作**：针对“待决策列表”中的每一个问题，大模型自动生成候选方案。
- **响应**：每个问题提供 2~4 个结构化选项（其中高亮一个推荐项），并始终保留一个“用户自定义输入框”以保证设计的灵活性。
- **交互**：用户完成所有问题的选择或填空后，底部【生成决策节点】按钮亮起。

### 阶段四：树形演化与状态派生 (Branching & Version Control)

- **操作**：点击【生成决策节点】。
- **响应**：在当前父节点下方生成一条连线和一个全新的子节点。
- **节点继承性**：该子节点包含了选中问题组合、各自的回答，并且隐式或显式地继承了从根节点到此处的全部决策历史。
- **平行宇宙（发散设计）**：
  - 用户可以随时回到任意历史父节点，对其进行重新回答，生成一个新的兄弟节点。
  - 用户也可以在历史父节点上发散全新的问题，生成另一个维度的子节点。它们在画布上并存，互不干扰。

### 阶段五：一键编译与方案生成

- **操作**：当某条决策链上的问题已全部解答，方案收敛到可接受阶段，用户可点击该叶子节点（或任意合法中间节点）上的【生成方案】按钮。
- **条件校验**：系统需校验该决策链无明显逻辑冲突且关键问题已解答。
- **响应**：大模型读取整条决策链的上下文，将其“编译”并输出为一份清晰、完整、结构化的产品设计文档（支持 Markdown、PDF 等格式）。

## 4. 交付给编码大模型的技术推演命题 (For AI Assistant's Next Steps)

> 注：请在阅读以上需求后，协助我进行以下技术方案的头脑风暴。

1. **前端画布选型评估**：在 React Flow、AntV X6 或其他基于 Canvas/SVG 的节点渲染引擎中，哪一个最适合承载这种高频交互、带有复杂内部组件（如节点内按钮、状态指示）的决策树？
2. **数据结构设计 (JSON Schema)**：如何设计一套健壮的节点和边（Edges）的数据结构？它需要既能适配前端画布的渲染，又能方便地递归向上追溯决策链历史，以便组装发送给 LLM 的 Context。
3. **LLM Context Window 管理策略**：随着树的深度增加，传递给大模型的决策历史会非常长。如何设计“上下文压缩”或“隐式状态聚合”的机制，防止触及 Token 上限或出现 Lost-in-the-middle 现象？
4. **大模型结构化输出 (Structured Outputs)**：在“阶段二”和“阶段三”中，大模型需要输出严格的 题目 -> 选项 结构以便前端渲染 UI。如何利用 Tool Calling / Function Calling 或 JSON Mode 来保障大模型输出的稳定性？
